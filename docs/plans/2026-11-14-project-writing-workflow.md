# 项目内写作协作的使用约定

状态为设计草案。用户已确认范围包含 Agora 主页与项目目录、当前项目的要求、偏好和反馈，不做跨项目的长期偏好。主页不阻挡从对话直接进入协作。本页提出预期行为，尚未实现。当前行为见[产品范围](../product.md)、[批注与生成](../flows/annotate-and-sync.md)和[审阅与写回](../flows/review.md)。

## 项目是什么

沿用现有的一份 Markdown 路径对应一个项目。项目保留工作稿、用户提出的要求、尚未完成的批注、历次候选与反馈，以及已写回的版本。重开同一路径后继续协作，换到其他文稿时不携带这些要求。主页列出多个独立项目，不把多份文稿合成一个项目。文件移动和一项目多文稿管理不在本轮范围内。

对话负责商量目标、补充事实和解释选择；稿纸负责编辑、选段批注、审阅建议和保存。用户不必在两处重复说明同一要求。稿纸继续保持现有纸面、页边笔尖、原位输入、建议回看和版本轨迹。

## 主页与直接协作的两条入口

同一个 Agora 面板提供主页与稿纸。用户打开 Agora、没有指定文稿时进入主页；对话中已经给出路径或明确协作对象时直接进入对应稿纸。主页负责找项目，不成为每次写作必经的欢迎步骤。

| 用户从哪里进入 | 到达哪里 | 预期结果 |
| --- | --- | --- |
| 打开 Agora，想找一份文稿 | 主页 | 看见简短欢迎说明和项目目录，选择后进入稿纸。 |
| 提供 Markdown 路径或明确要求打开某项目 | 对应稿纸 | 直接恢复该项目，不先到主页再选一次。 |
| 从对话开始一篇新稿的共同写作 | 新项目稿纸 | Agent 建立 Markdown 后直接打开，已有对话信息成为本稿要求，不另走主页或强制填表。 |
| 明确继续当前或最近一次协作 | 对应稿纸 | 恢复原来的编辑或审阅进度；对象不明确时才展示项目选择。 |

主页沿用稿纸的安静视觉：简短欢迎说明、最近协作的项目列表，以及打开 Markdown、开始新文稿的入口。首次没有项目时说明如何开始；已有项目时以继续写作为主，不重复大幅引导或产品介绍。开始新文稿沿用对话建立稿件的流程，不在主页增加一套写作问卷。

每个项目显示可辨认的标题、文稿位置和最近协作记录，以及上次保存的状态，例如有草稿、待审阅、仍有待改意见。同名项目用位置区分。无法确认实时进度时显示上次状态，不能把旧记录标成仍在生成。目录只收录用户通过 Agora 打开的文稿，不扫描其他文件夹，不从其他项目提取偏好。

从目录选中项目，恢复工作稿、本稿要求、批注、选择和历史，不自动保存、清理批注或重新生成。原来停在审阅，就回到审阅；停在编辑，就继续编辑。找不到原文件时保留项目记录并提示路径问题，不另建空稿替代。项目由其他活动对话占用时明确提示，不自动抢占。

稿纸保留现有徽记菜单，在原有操作区增加轻量的“项目目录”入口，不把点击徽记直接改成跳主页。返回目录只是切换视图，不结束审阅、不撤销选择、不取消生成，也不写原文件。另开项目不会改变已经打开的其他稿纸所属的文稿，迟到的产物仍只能交回原项目。

实现时需要区分“打开主页”和“继续最近文稿”的入口意图，保留现有省略路径可恢复最近项目的约定。首页读取已知项目的目录信息，不为列出项目逐个启动服务或绑定文稿；打开选中的项目时才建立对应协作。已有项目应能出现在目录中，不能只记住新增主页之后创建的项目。现有最近项目恢复机制见[桌面接入](../../plugins/desktop/README.md)，具体宿主入口仍需安装包验证。

## 开始与继续写作

已有文稿时，提供绝对路径即可打开项目。明确要求用 Agora 协作时，Agent 直接承接。在同一项目中说“继续改”，沿用已记录的要求与反馈，不重新做一遍问卷。

从零共同写作时，一旦明确要用 Agora，Agent 就建立 Markdown 并打开稿纸，可以从空稿开始，已有信息直接带入本稿要求。必要的问题在当前对话继续讨论，不必先填完信息或生成长文再搬到稿纸。建立位置沿用已选工作目录或宿主已有的文稿存放约定，并告诉用户实际路径。缺少目的或事实时才追问，不为开始协作强制填写完整产品表单。普通的一次性问答不自动创建项目。

首稿可以依据本稿要求生成，不以已有选区批注为前提，也不制造一条假的选区批注来启动。Agent 产出的第一版同样作为可审阅的候选交回，不能未经选择就写回原文件。此处是需要新增的写作能力，当前批注生成协议仍要求有效批注；实施时必须分别明确首稿与按批注改稿的请求意图。

Agent 把用户已明确的用途、受众、事实、语气和禁止事项整理为“本稿要求”。例如充电宝项目包含电商用途、轻薄与双向快充、轻松有趣，以及兼顾极客与优雅、避免排斥部分受众。未给出的容量、功率和厚度不补成事实。

“本稿要求”在现有文稿操作中有简短的可查看入口，展开后允许改写、停用和删除。它不混入正文或导出的 Markdown。常规改稿直接沿用；只有发生变化时，才简短说明本次新增或调整的要求，不要求用户每轮确认。

## 看见建议后的使用方式

| 用户的意图 | 提供的操作 | 正文、批注与反馈的结果 |
| --- | --- | --- |
| 这处建议合适 | 接受 | 按原交互收起成所选正文，保留页边回看；暂不写原文件。 |
| 先不用这次方案，但这条意见还要继续改 | 先保留原文 | 沿用原句，保留对应批注为待改目标，记录这版未被采用，不自动推断原因。 |
| 这一版整体不合适 | 换一版 | 无须逐条拒绝，沿用当前目标，带上本版候选及已有反馈，再生成另一版。 |
| 想先自己写，或不继续看建议 | 继续编辑 | 把已接受的预览保留到工作稿，收起其余建议，未解决的批注折叠为待改意见，不自动发起生成。 |
| 明确拒绝，不再修改这条 | 这条不改了 | 结束并归档对应目标，不再显示为当前批注，不再作为待改任务交给 Agent；历史可回看。 |
| 这轮剩余建议对应的修改都不再需要 | 这几处不改了 | 一次结束本轮剩余建议明确对应的目标，归档这些批注；已经接受的内容与手改保留。未获建议或关联不明的意见继续待改。 |
| 先离开，稍后再来 | 关闭面板或退出 Codex | 保留稿件、当前选择和进度；重开恢复，不要求先执行“结束审阅”。 |
| 当前正文值得留下 | 保存 | 写回并读回核对后登记版本；尚未完成的修改目标可以继续保留。 |

“结束审阅”不再承担日常继续写作的主要入口。用户面对的是接受、换版、继续编辑和保存这些写作意图。整轮“换一版”和“继续编辑”需要在审阅状态可发现，不能只靠用户猜徽记含义。具体露出方式需在原有操作区验证，不增加常驻大工具栏或独立设置页面。

审阅期间可以对本轮建议补充反馈，沿用页边输入的语言和操作。反馈属于这轮候选，不假装是对原文的新选区批注。用户可以不填写原因直接换版。局部“只重写这一处”的生成范围留到后续，本轮先完成整轮反馈与换版。

拒绝和先保留原文是两种明确的意图。用户选择拒绝时结束对应要求，选择先保留原文时继续保留该要求。界面不并列两个含义相近的“拒绝建议”和“保留原文”让用户猜差别，而用“这条不改了”说明拒绝的后果。结束修改目标沿用批注管理或整轮操作，不在每项差异旁堆四个同等按钮。批量操作说明对应的目标范围与数量；未回应或关联不明的意见不因用户拒绝其他建议而消失。结束目标不自动撤销此前已接受的正文，撤销仍通过本轮页边回看改选。

在当前审阅内，接受或保留原文后的页边回看继续支持改选。“继续编辑”后，旧候选作为历史尝试保留，只读回看，不把旧建议直接覆盖到后来编辑的正文。下一轮以当前工作稿重新生成。

## 换一版保住什么

全不满意时，基于本轮人类底稿重写，不把被拒绝的 AI 文本当成新的正文。部分接受时，保留已接受的内容，并重写尚未接受的部分。用户已接受的内容默认不再修改；若它与新的明确要求冲突，先指出冲突，让用户决定是否重新开放。

写作者在生成前拿到当前底稿、本稿要求、待改意见、本版候选和对应的反馈。新候选仍需展示实际差异，不能仅给一段聊天回复。大幅重写的口号采用完整句子对照，少量字词变化保留细节标记；选择编号和可独立选择的修改不因显示方式改变。

换版期间仍保留上一版及其选择。生成失败、取消或没有新建议时可以回到它，不要求重做已有选择。只有新的有效候选交回后才切换审阅。迟到的旧产物或旧总结不能覆盖新的正文、要求与反馈。重复触发同一次请求不创建重复候选。

候选尝试与正式保存的版本分开。换版、反馈、接受和继续编辑都不写原文件。审阅中仍有待选项时，不把它们默认为接受；用户可以先“继续编辑”保留已选预览，再决定是否保存。

## 批注怎样收起与完成

批注至少区分“待改”“已有建议，待判断”“已完成”和“已撤回”。选区还能否准确定位是另一件事，不能把选区有效当作需求完成。

新批注是待改意见，生成后进入待判断。用户选择先保留原文或换版后，原目标继续待改，并带上刚才的反馈。用户明确拒绝则结束并归档对应目标。返回编辑只改变工作方式，不反转这些选择；尚未表态的意见折叠为待改标记，不把旧意见重新摊开成一批新批注。

每轮记录哪些意见有对应建议，哪些未被回应或仍无法定位。只有与批注明确关联的全部建议被接受后，才自动收起完成该条意见。关联不清、部分接受或仍有被保留原文的相关建议时，不自动清掉它；用户也能明确标记完成或结束这条要求。单项差异的选择不能被猜作整条批注的撤回。不能因接受一处建议而清理本轮全部批注，也不能假设一条批注只对应一处修改。

已完成和撤回的批注进入回看，后续生成不重复提交。未解决的意见允许跨保存继续存在，但只在用户再次发起改稿时送给 Agent。正文编辑后选区失效的意见保留目标与反馈，待重新关联后再改写，不能搜索到同样文字就自行认定位置。

## Agent 怎样获得经验

本项目同时保留三类信息：用户已明确的本稿要求、每轮实际采纳和拒绝的记录、由记录支持的下一轮调整方向。它们都只作用于此项目，不建立跨项目用户画像。局部意见和反馈默认跟随对应目标，不自动提升为持续生效的全稿要求；用户明确表示整篇适用时，才进入本稿要求。

用户在纸面上的取舍立即记录。Agent 下次生成前读取这些记录，整理本项目的调整方向，再据此改稿；不因每一次点击就唤醒一次 Agent。用户暂时离开时，记录仍能保留，不依赖后台总结是否完成。

用户说“副标题太普通”，先归入这条目标的反馈；只有明确说“这篇稿子都要避免泛泛的口号”时，才作为整稿要求。只选择先保留原文时，只能记录这次提案未被采纳，下一版避免原样重复，不得自行认定用户永久讨厌某个词或某种风格。

明确拒绝的目标从后续待改任务排除，其局部反馈也不再作为活跃修改指令。Agent 可以把历史结果作为本项目的参考案例，但不能借“总结经验”重新打开已结束的修改范围。用户后来明确要求重新修改时可以开启新目标。推测出的创作方向只用于当前仍待处理的范围，不能覆盖用户明确的定位。

以充电宝项目为例，下一轮的简短说明可以是“保留极客与配饰定位，避免主标题产生品类歧义，副标题换一个更有辨识度的表达”。它说明可执行的调整，不展示长篇自我评价，也不把受众包容性误写成“女性不喜欢科技感”。用户可以查看和修正本稿要求及调整方向。

每轮使用生成时的要求与反馈快照。生成过程中用户补充的新要求保留为较新的记录，不被旧产物覆盖；本轮展示其依据的要求，后续生成使用新要求。明确的新要求优先于旧偏好，事实冲突或彼此矛盾的硬要求需要单独核对。

## 预期效果与验收

- 未指定文稿地打开 Agora，看到欢迎页和项目目录；第一次没有项目也知道如何开始，打开后续项目仍可从目录找回旧稿。
- 从对话提供路径或建立新稿，直接到协作稿纸，不经过目录或重复填写已说过的写作信息。
- 两个同名文稿可以按位置区分；选择项目恢复它自己的进度和要求，不混入另一项目的批注与偏好。
- 从审阅返回目录再打开，原来的选择仍在；切换项目不取消另一项目的执行，旧产物不交到新稿件。路径失效或项目占用明确提示。
- 打开同一路径继续写，Agent 能说清当前用途和定位，不要求重述已确认的信息；打开另一文稿不套用本项目的要求。
- 三处建议都不喜欢，可以直接换版，不必点三次保留原文再退出，也不必重写三条批注。下一轮实际收到前版与反馈。
- 只接受第一处，再换一版，第一处保持，其他部分重新提出；生成失败时仍能回到原有选择。
- 返回编辑后，工作稿保持可写。选择先保留原文的意见收为待改标记；明确拒绝的意见从当前批注归档且不再生成，未完成的要求不会因别处被采纳而消失。
- 三条意见只得到两条回应，批量结束这两处后，第三条仍然待改并可见。局部“副标题太普通”的目标被结束后，下一轮不能因自动总结又重新改写该处。
- 只有拒绝行为、没有理由时，项目记录承认原因未知；Agent 不编造用户偏好，不重复原样交回被拒候选。
- 保存可以留下当前阶段的正文；未完成目标不阻碍之后继续协作。重开仍能恢复项目要求、反馈和进度，正式版本只在成功写回后新增。

## 取舍与下一步

已比较三种方向：保留“结束审阅”并增加重试入口；以接受、换版和继续编辑组织现有稿纸；每轮完成后先展示一个总结确认页面。推荐第二种。第一种仍需用户理解内部轮次，第三种增加每轮必经步骤。

本轮先定产品使用约定，后续按同一份充电宝文稿验证入口与反馈交互，再制定实现计划。项目要求、批注状态、候选尝试和写回版本的职责需要在实现设计中分别明确。当前服务和面板职责见[代码分工](../architecture.md)，实施后同步产品与流程说明。本草案不表示新行为已经上线。
