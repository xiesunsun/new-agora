# 仓库与命名约束

本页约束 Agora 的开发目录、Git 分支、worktree 和源码命名。具体模块职责见[代码分工](architecture.md)，操作命令和审阅证据见[开发与审阅](development.md)。

## 开工记录

每轮变更先按[任务收尾协议](development-lifecycle.md)建立任务目录，再记录以下内容。可放在任务说明、实施计划或 PR 中，基线文件进入受管状态目录。

- 用户指定的主项目目录、实际执行目录、分支和 `HEAD` 完整 SHA。
- 集成目标分支、起点分支和起点的完整 SHA。依赖未合并变更时，记录父分支与父 PR。
- 已有改动的归属及[基线清单](development.md#固定开发基线)。
- 本轮负责的文件、共享契约负责人和可观察的验收结果。

`main` 是集成分支。需要远端状态时先 fetch，再记录 `origin/main` 的 SHA。不能把本地 `main`、远端跟踪引用和当前工作分支当成同一个版本。已接受的基线用提交 SHA 表达，确有长期标记需要时用有说明的 tag。

## 分支与 PR

新增工作分支使用 `codex/<type>-<topic>`。`type` 从 `feat`、`fix`、`refactor`、`docs`、`test`、`chore`、`perf` 中选择。`topic` 使用小写英文和连字符，描述本轮结果，例如 `codex/fix-save-recovery`、`codex/docs-repository-governance`。

场景编号、视觉方案名和临时状态不单独充当任务名称。A01 放在验收说明中，`baseline` 放在基线记录中。提交标题使用 `type(scope): subject`，说明实际改动。

每个分支交付一个可审阅结果。独立变更从已接受的集成基线开始，PR 面向 `main`。依赖未合并实现的变更从父分支的明确 SHA 开始，PR 面向父分支。父 PR 合并后，重新核对依赖、调整子 PR 的基分支并运行检查。修复归入引入问题的变更，再向依赖分支传播。

切换当前目录的分支前，核对已有改动和运行中的进程。不得用 reset 或覆盖文件来获得干净状态。重写已推送历史时核对远端变动，只能使用带明确预期的 lease；对共享分支的历史重写先取得授权。合并、部署和删除分支按该任务已有授权执行。

本规则适用于新增分支。既有名称先登记和核对，改名时同步 PR、worktree 和引用，不能为了通过命名审查丢弃已有工作。

## 主目录与 worktree

主项目目录是用户指定的长期管理入口。普通串行任务直接在该目录的工作分支完成。创建 worktree 用于同时保留独立分支的文件状态，例如并行实现、隔离复现或集成验证。创建前写明用途，不能因为执行计划就默认另建一个项目目录。

项目自行创建的 worktree 使用主目录同级的 `<项目目录名>.worktrees/<type>-<topic>`。例如主目录为 `/code/new_agora` 时，工作目录为 `/code/new_agora.worktrees/fix-save-recovery`。应用托管的 worktree 路径由应用决定，必须记录实际路径和托管方，不能把生成的路径当成新的主项目位置。

每个新增 worktree 记录负责人、分支、基线、用途、验收结果和回收条件。一个 worktree 由一个负责人协调写入。并行代理的接口与文件归属遵循[开发规则](development.md#写代码和测试)。

隔离文件状态后仍要分开端口、运行目录、数据库和测试文稿副本。创建 worktree 不会自动隔离这些资源。

聊天绑定的目录、终端的当前目录和 Git 检出分支分别核对。创建 worktree 不表示可以移动聊天或改变主目录。需要改变这些位置时，先说明目标和原因。用户指定了执行目录后，后续命令显式使用该目录。

任务交付后核对 worktree 和分支。回收前确认没有未归属的文件、未保存的改动、运行进程、依赖该分支的未合并 PR，且提交已被保留或明确放弃。使用创建它的管理工具回收。仍被活动聊天引用或工具拒绝回收时，登记保留原因。不得直接删除目录来绕过管理状态。

## 源码层次与命名

Agora 当前只有根目录的一个 npm 包。`apps`、`packages` 和 `plugins` 下的目录是源码模块，是否独立安装、构建和发布由实际配置决定。不能从目录名推断它们是独立项目。

| 目录 | 放入的职责 |
| --- | --- |
| `apps/<role>` | 可运行产品入口及其所属业务实现 |
| `packages/<capability>` | 被当前调用方共享的契约或库，通过公开入口导出 |
| `plugins/<host>` | 宿主集成、协议转换和插件入口 |
| `dev/<tool>` | 开发场景、mock、模拟执行与故障配置 |
| `scripts` | 构建、检查和本地启动命令 |
| `tests` | 验收与回归测试，使用正式模块入口 |
| `docs` | 当前说明、决策和计划 |
| `evidence` | 指定提交或构建的验证记录 |

新增目录使用小写英文和连字符。名字描述已经存在的职责。实现机制只在需要区分多个实现时加入名称。不用 `v2`、`new`、`next`、`final` 或视觉探索代号区分长期实现。原型保存在仓库外的探索目录，正式接入后迁移调用方并移除被替换实现。

正式产品、模块和框架名要有明确的命名选择。接受原型交互或迁移方案不自动把探索代号升级为正式术语。历史证据可保留来源名称，当前代码和说明使用职责名称。

先选择已有模块。只有职责或运行边界需要独立维护时才拆模块。新增模块要在[代码分工](architecture.md)中说明责任和调用方向，提供 README，并同步[依赖规则](../.dependency-cruiser.mjs)及违规样例。模块移动时一起迁移导入、构建入口、测试和说明。

类型名也表达实际职责。`Controller` 接受操作并协调状态，`Store` 拥有一份数据及其读写，`Transport` 转换通信边界。只有实际管理跨调用的执行和生命周期时才使用 `Runtime`。不要因为将来可能扩展就预先建立通用 `Manager`、注册中心或框架层。

现有目录与新规则不一致时，在有范围、有验收的变更中迁移。当前遗留项见[本次核对记录](../evidence/repository-governance/README.md)。

## 检查与例外

当前 `pnpm check` 检查格式、lint、类型、依赖边界、测试和文档链接。任务收尾、有限 hook 续跑、工具限制与受管资源清理有违规样例测试。分支命名、worktree 归属及回收条件仍由开工记录和 PR 审阅核对。

新增可机械检查的约束时，把检查接入 `pnpm check`，用违规样例证明会失败。任务、目录或模块的例外要在 PR 中说明原因、负责人和退出条件。例外不能变成第二份规则来源。
